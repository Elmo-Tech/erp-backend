## Lock protocol proposal / important limitations

1. Header row (`journal_entries`) FOR UPDATE, by exact company+entry UUID; serializes competing header checks. Company FOR SHARE, fiscal-year FOR SHARE, period FOR SHARE, currencies code sorted FOR SHARE, own-company account UUID sorted FOR SHARE, then read-only line aggregate. All in one transaction; no posting mutation or child locking.
2. If a period closes or an account deactivates before its row is acquired, shared locks wait and the state is rechecked; if held afterward, closure/deactivation waits. This protects the locked parent/account metadata inside the validation transaction only.
3. **Unresolved:** child UPDATE can acquire tuple before the P0-04A BEFORE ROW trigger obtains header. Future posting header→child FOR UPDATE risks a deadlock. Current read-only aggregate has no child tuple lock; it does not guarantee that lines remain immutable for a future posting service. Need reviewed and proven ordering with actual posting-vs-line-write concurrency negatives before enabling status change.
4. P0-03 FX CHECK permits NULL UNKNOWN; eligibility SQL explicitly uses `IS NOT TRUE` and denies incomplete FX. DB-level migration hardening remains OPEN. Runtime TRUNCATE/DDL/trigger-disable privileges remain NOT VERIFIED. Transaction isolation + trust boundaries for real posting NOT IMPLEMENTED.
