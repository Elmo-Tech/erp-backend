## Trust boundaries / attacker model

| Boundary | Trusted component and assumption | Attacker action / required failure behavior |
| --- | --- | --- |
| Browser → Laravel | Authenticated first-party Sanctum session, verified MFA where required, CSRF, server-side role+membership authorization; selected company is **untrusted input** | Tamper with session/company choice; must not authorize a different legal company |
| Laravel → PgBouncer → PostgreSQL | SQL sent by runtime LOGIN `p003c_runtime`, under transaction pooling. Pool is a transport, not a tenant authority | SQL injection, unsafe raw SQL, compromised job, or malicious callback can execute `set_config`, joins, ad hoc SELECT/UPDATE and transaction changes with all runtime grants; no expectation that arbitrary runtime SQL is benign |
| Runtime DB role → protected data | Distinct non-owner, NOINHERIT, NOBYPASSRLS, no owner-role membership, no schema CREATE; table/column/function grants explicitly allowlisted | Must deny migration ownership, DDL, SECURITY DEFINER replacement, role switch and forbidden tables/columns. This alone **does not authenticate tenant identity** |
| Runtime role → special security function/key | Key table and verifier owner separate from runtime, schema CREATE revoked; carefully fixed `search_path`, schema-qualified relations/functions, no signer callable by runtime | Must not allow key SELECT, signer invocation, function replacement, function hijack or forged claims. Privileged function code and every nested function/role privilege require external review |
| Transaction → next request/worker | `SET LOCAL`/transaction-local claim; outermost transaction; fresh authorization; row locks for revocation ordering | Failed work rolls back; pooled connection and reused worker never transfer context. Transaction lifetime and stale/duplicated signatures must be bounded |
| Cross-company finance/HR | Egypt/Italy separate legal company IDs with server-approved permissions and composite foreign keys | Both EG→IT and IT→EG read and write must fail. Central-management or project assignment is not automatically legal-ledger authority |

**Assets:** EG/IT ledger/payroll/HR data, user and MFA secrets, user membership and company role state, sessions, queue payloads, audit evidence. **Out of scope for a SQL-bound tenant guarantee:** compromise of the trusted issuer's signing secret, DB owner/superuser, operating-system deployment credentials, or compromised backend code that already has privileged signing capability. Those scenarios require separate incident controls and cannot be made impossible by GUC or RLS alone.

## Findings and architecture alternatives

1. **FAIL (proven in P0-03C):** RLS policy `company_id = current_setting('app.company_id')::uuid` is bypassable by a runtime SQL actor via `set_config`, even with `NOBYPASSRLS`. Checking the setting at transaction end cannot undo leaked reads. A custom GUC is not authorization.
2. **Recommended now — explicit company-scoped authorization:** Resolve *live* actor, legal membership, active company and permission in trusted Laravel code, lock relevant rows when revocation ordering matters, and require every legal query to use the authorized `company_id` predicate. Retain composite FK/DB invariants; keep raw finance relations **ungranted** to the runtime role until full review. Risks: omitted predicates/raw queries, SQL injection under a role with broad SELECT, unreviewed background/service-account paths. Require per-endpoint query review and negative EG/IT tests. **This is an interim application-level boundary, not a guarantee against arbitrary SQL with unrestricted table grants.**
3. **RLS as additional layer only:** May reduce damage from accidentally omitted filters, but do not deploy GUC-only policy. Any accepted RLS must derive authority from a DB-verified identity source and be tested under actual non-owner runtime, PgBouncer, jobs, concurrency, and UPDATE/INSERT `WITH CHECK`. Its presence does not waive application authorization.
4. **DB-side signed claims / privileged verification (research candidate):** Distinct privileged issuer signs `company_id | authenticated_actor_id | transaction_id`; owner-held secret and `SECURITY DEFINER` verifier validate MAC and live actor/membership, fail closed; runtime only EXECUTE verifier, not sign/read key/CREATE. `database/security/p003d_signed_claim_disposable.sql` is **a disposable, owner-simulated issuer experiment ONLY**. It demonstrates rejection of altered/unsigned GUC claims in one transaction if its SQL test succeeds; it does **not** prove a real unforgeable end-to-end identity, secure signer, non-replay across transaction IDs, bound session/principal, permission scope, race-safe revocation, rotation or compromised-runtime resistance. Transaction IDs are observable; the signature/issuer secret supplies integrity. A bearer claim copied within the same transaction can still be replayed and a trusted signer that accepts caller-provided actor/company would become a confused deputy. No production signer API or credential is implemented.
5. **Database-per-company or separate per-tenant DB credentials:** Stronger SQL-level role isolation, with operational/connection/reporting overhead and migration complexity; shared-schema ADR-003 would need separate owner approval if changed. **Not selected.**

**Recommendation for ADR-022:** keep **PROPOSED**; application-verified company predicates + strict per-relation GRANTs + composite FKs are required today. Neither permanent RLS nor a trusted DB context can be approved until independent review and verified end-to-end issuer provenance. Treat the signed-claim SQL as a falsifiable exploration, not final architecture.

## Current runtime GRANT matrix (observed scripts, NOT production-approved)

| Object(s) | Current CI runtime allowance | Legitimate use / risk / incomplete verification |
| --- | --- | --- |
| Database `elmo_erp_test`, public schema | CONNECT, USAGE; no schema CREATE | Login/query; inspect default schema PUBLIC grants and future schemas/functions before release |
| `users` | SELECT all columns; UPDATE(`updated_at`) | Authentication reads and row lock; full-column SELECT includes password hash and MFA secret; direct timestamp modification is possible. **HIGH least-privilege gap** |
| `companies` | SELECT all; UPDATE(`updated_at`) | Company selector + joined row lock; timestamp writes possible |
| `company_memberships` | SELECT all; UPDATE(`updated_at`) | Fresh membership lock; status/company writes denied but timestamp writes possible |
| `company_role_assignments` | SELECT all; UPDATE(`updated_at`) | Role-row lock; role_key/company writes denied but timestamp writes possible |
| `global_role_assignments` | SELECT only | Global role lookup; no role mutation |
| `sessions` | SELECT, INSERT, UPDATE, DELETE | Database session store; compromise can alter raw session payload; authenticated HTTP test is not a security sign-off |
| `jobs`, `failed_jobs` | SELECT, INSERT, UPDATE, DELETE; sequences USAGE, SELECT | Queue polling/claim/retry and failed-job logging; runtime may modify arbitrary queue payloads. **High integrity scope**, split queue worker identities/separate database roles later |
| `user_mfa_enrollment_authorizations` | **NO GRANT** | Enrollment confirmation consumes `consumed_at`; workflow likely fails as restricted runtime. Test needed |
| `user_mfa_recovery_codes` | **NO GRANT** | Recovery consumes/deletes code and enrollment issues codes; fails under current runtime grants |
| MFA columns on `users` | **NO UPDATE on `mfa_secret`, `mfa_last_step`** | Existing MFA confirmation/verification requires controlled mutation; unrestricted writes are unsafe. Requires narrowly scoped security workflow role/function and adversarial tests |
| `password_reset_tokens`, `job_batches`, `cache`, `cache_locks` | **NO GRANT** | Corresponding flows not fully tested against restricted role; either intentionally disabled or require separate principal |
| `fiscal_years`, `accounting_periods`, `ledger_accounts`, `journal_entries`, `journal_lines` | **NO raw SELECT/DML** | Intentionally blocked. No ledger posting API authorized |
| Other schema tables (audit/outbox/idempotency etc.) | **NO default table grants in p003c role script** | Future features must have per-table/column access inventory, not blanket ALL |
| `p003d_private.keys`, verifier | Probe-only owner key; runtime EXECUTE verifier, NO key SELECT/CREATE, rolled back | Not a production grant or permanent function |

**Important:** PostgreSQL `SELECT ... FOR UPDATE` requires UPDATE privilege on locked relations, and existing joined `companies` is locked. `UPDATE(updated_at)` is *not* inert: it allows write-time tampering on the four tables. Explore `FOR SHARE`/appropriate lock strengths with verified revocation serialization or a restricted privileged auth function; **do not remove UPDATE grants without testing**. The current code is not fully compatible with a single restricted runtime for Auth+MFA; CI must test missing privileges as expected denial rather than falsely call these workflows supported.
